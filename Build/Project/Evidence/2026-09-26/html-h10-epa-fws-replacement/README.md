## FWS: CSS scope and lossy WebP gaps

The FWS archive captured 46 resources and all 27 page images without a pending image. Offline Chromium prints seven pages and screen-media prints eight; PeachPDF prints seven. All OfficeIMO PDF intents stop at the default CSS rule limit (`actual=10001`, `limit=10000`). An exploratory replay with a 20,000-rule limit also stops at `actual=20001`; it was not adopted as a new untrusted-input policy. No OfficeIMO FWS PDF or six-target editable acceptance is claimed. The default bound remains unchanged.

At clean code head `52260adbb9bcb871db1988fb9d2755d70914a654` (unchanged renderer code through documentation head `d790d1f377556fcb3e1dfeaff30a705c1ef4a520`), an offline CSSOM probe found 12 readable stylesheets containing 24,007 style rules: 21,526 active in screen media and 21,521 active in print media. A simple comma-split selector count found 28,518 active print selectors; that count can overcount commas inside functional selectors and is not a parser acceptance metric. The 20,000-rule rejection therefore cannot be dismissed as a false cap merely from the page's visible size.

An explicit exploratory `MaxCssRules=40000` allows default print conversion without changing the untrusted profile. Two initial runs took 7.4–7.8 seconds inside the probe and allocated about 4.76 GB cumulatively; `/usr/bin/time -l` recorded maximum resident memory of 442,286,080 bytes on this Mac. A further diagnostic replay took 11.5 seconds and produced the same 1,847,721-byte PDF, SHA-256 `47bb5f6e1e671085bd67422f66719391a0afae372944be903bf451d016940d18`. These are exploratory single-machine observations, not a platform budget qualification.

OfficeIMO prints five pages against Chromium's seven. All five OfficeIMO and seven Chromium pages were inspected: the Florida salt marsh vole, alligator, bog turtle, brown pelican and bald eagle photographs are absent from OfficeIMO, while the later story-card photographs paint. Every missing photograph is present in the frozen archive as a 992-pixel responsive WebP resource. RIFF inspection identifies a lossy `VP8 ` chunk in each; none is lossless VP8L. The shared managed decoder explicitly supports lossless VP8L only. The PDF report contains exactly five `HtmlPdfImagePayloadOmitted` warnings for these images, with omission loss, but its generic preparation message does not identify the codec limitation.

The initial vector-PDF preparation bypassed the configured `IOfficeRasterImageCodec`, separately from the missing managed VP8 decoder. The bounded optional decode contract and the typed `CodeGlyphRasterImageCodec` bridge now serve ordinary and rasterized drawing images. Container validation, resource limits, source dimensions and cancellation apply before/after the synchronous provider call. Static-frame selection reports animation/page loss, including direct APNG and flattened drawing effects; visible missing-image placeholders remain outside source-pixel validation. No captured photographs were replaced with JPEG derivatives.

A shared-owner reuse probe at CodeGlyphX `31704b636f30c8608f4b416cc6a6fe64a134eeae` successfully returned pixels for all five archived VP8 photographs, but independent Pillow/libwebp comparison found mean absolute RGBA errors of 28.6–73.3 on the 0–255 channel scale. The returned eagle image was inspected and is visibly corrupted. Decode success alone therefore does not qualify that provider. The isolated `fix/webp-vp8-fidelity` worktree starts at CodeGlyphX base `11f166db`. Its local repair corrects control-partition/header parsing, coefficient entropy decoding and context retention, macroblock and directional prediction, padded reconstruction, and chroma/color conversion against [RFC 6386](https://www.rfc-editor.org/rfc/rfc6386). Four independent Pillow/libwebp-produced fixtures cover solid colors, a directional grayscale pattern, and an odd-size color image; all pass the predeclared mean channel error of at most 1 and maximum error of at most 3. The final replay of the five archived photographs has mean RGBA channel errors of 0.0174–0.0391 and maximum error 1 on the 0–255 scale. All five reference/candidate pairs were visually inspected. At CodeGlyphX candidate `b29cf593d31b42f644a09d8ca50341f5bc3e2f1a`, independent encoder interoperability also preserves solid colors and the selected smooth/patterned images: native/managed decoder differences remain at most one channel value. The repaired encoder uses whole-block prediction, corrected entropy coding and integer forward transforms. An independent whole-codec review found incorrect loop-filter delta bounds and truncated oversized VP8 dimensions; both were reproduced and fixed, with targeted confirmation covering still and animated fallback paths. All 112 WebP tests pass on .NET 8 and .NET 10, and normal multi-target Release packaging includes the required third-party notices and license files. Broader validation is not green: initial suites had missing image fixtures and PNG/QR scan failures, and a subset on unchanged base `11f166db` reproduces those scan failures. The repository fixture download closes the missing-input failures. The sequential .NET 10 rerun has 1,462 passes and three failures: two artistic QR cases and a default DataBar scan deadline. All three reproduce on unchanged base; the DataBar deadline also reproduces in isolation on the repaired candidate. [CodeGlyphX PR #248](https://github.com/EvotecIT/CodeGlyphX/pull/248) carries this owner repair, with CI and automatic review pending at publication. These results qualify the selected codec paths, not the complete image corpus. The OfficeIMO integration proof uses the existing local CodeGlyphX project-reference override; it does not establish the behavior of a published provider package. Local probe sources, baseline and current candidate metrics, original image bytes and the final comparison raster remain in `h10-fws-webp-owner-probe/`; they do not replace the frozen MHTML input.

At OfficeIMO `df60a2ca06f12eaa6dc57089334bfed80d11fecf`, using CodeGlyphX `b29cf593d31b42f644a09d8ca50341f5bc3e2f1a`, all five original VP8 photographs match decoded PDF-embedded pixel hashes in each intent. Print produces five pages, screen-media six, and snapshot six, with zero image-payload omissions. All pages were visually inspected against the retained seven-page Chromium print reference: photographs are restored, but their print width and section/page grouping still differ. The follow-up image/loss fixes at `e291e1a0d` produce byte-identical PDFs for all three intents. H4 at the first integration head passes all eight cases; that bounded gate does not qualify this unfamiliar archive.

A separate print probe records 30,506,448 allocated bytes for archive loading, 4,986,419,088 through PDF serialization including loading, and another 409,341,128 for readback and pixel-hash validation. Wall-clock measurements ran alongside builds and are unsuitable as acceptance timings. `PeakWorkingSet64` reports zero on this host, so peak resident memory is unavailable in this probe. The explicit 40,000-rule CSS cap remains exploratory. A default-resource qualification requires a measured CSS-scope decision, conversion-only budgets, and supported-platform resident-memory sampling.
