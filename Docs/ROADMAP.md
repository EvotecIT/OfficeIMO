# OfficeIMO roadmap

This is the repository's single product backlog. It contains open work only. Implemented behavior is documented in package READMEs, support matrices, generated inventories, and current-state guides linked from [the documentation index](README.md).

An item belongs here when it has a clear product outcome and an owning package. Implementation checkpoints, completed task lists, release-wait notes, architectural rules, and comparison tables do not belong here.

Deliberately bounded compatibility contracts are not backlog by themselves. A preserved or rejected profile with a documented diagnostic becomes roadmap work only when the repository adopts a concrete supported shape and evidence plan for it.

## Release-wide quality

- [ ] Extend the generated Office compatibility catalog beyond the current Word, Excel, and PowerPoint legacy-format families into a package-neutral operation model for create, read, edit, preserve, inspect, convert, export, reject, and unsupported behavior.
- [ ] Generate compatible package README sections, website capability pages, MCP discovery, and support matrices from that model wherever one source can truthfully own the claim.
- [ ] Expand cross-producer fixture corpora with producer/version provenance and stable package or semantic diff policies.
- [ ] Add reproducible correctness, file-size, elapsed-time, peak-memory, allocation, cancellation, and deterministic-output evidence for representative workloads on every supported operating system.
- [ ] Add an opt-in Arrow C Data Interface stream bridge in `OfficeIMO.Data.Arrow` only with explicit unmanaged-lifetime ownership, bounded record-batch callbacks, cancellation, importer round trips, and native-consumer evidence. Keep the current managed `DbDataReader` batching API dependency-isolated and do not expose raw pointers without a fail-safe release contract.
- [ ] Extend typed loss classification and strict acceptance evidence across the remaining native format-projection owners. Sweep resource, font, pagination, SVG, and format-bridge diagnostics; preserve the specific loss category across composed routes and reject loss before publication. Source reports that expose only aggregate HasLoss need a common typed diagnostic contract before downstream policies can distinguish omissions from approximations.
- [ ] Establish an all-page conversion consistency gate over the existing Drawing scene and format owners. Cover DOCX, XLSX, PPTX, HTML, PDF, Visio, OneNote, email, EPUB, ODT, ODS, and ODP to SVG, PNG, JPEG, TIFF, and WebP with identical page selection, layout profile, font bytes, shaping provider, dimensions, DPI, background, and resource policy. Compare direct raster output with independently rendered SVG and PDF, then compare all three against source-producer or labelled semantic evidence so matching outputs cannot hide a shared import loss. Gate text and object coverage, crop/rotation, clipping, gradients, alpha, images, page counts, and diagnostics; allow encoder-specific visual tolerances only after geometry and content pass.
- [ ] Extend the canonical conversion catalog to distinguish direct routes, explicitly composed routes, and unsupported source/target pairs. Assess Markdown, RTF, MHTML, AsciiDoc, and LaTeX image output through existing HTML/PDF owners before adding convenience routes. Include SVG input and raster-image transcoding with explicit page/frame, color, orientation, metadata, vector-text, raster-embedding, and resource contracts. A PNG embedded in SVG must not be described as recovered vector geometry; a route listed for discovery must separately declare execution support in each host.
- [ ] Make conversion performance claims depend on passing the same content, geometry, visual, and requested compliance contract for every measured implementation. Extend the existing BenchmarkDotNet and PowerForge evidence lanes with current package versions and hashes, font/profile provenance, fixed CPU-domain metadata, cold-start versus warm-throughput boundaries, per-scenario statistical error, process-tree/native memory, and output size. Refresh 1/20/100-page and payload workloads on Windows, Linux, and macOS, add representative non-HTML route budgets, and retain slower or failed cases. Close a speed objective only when the selected equivalent workload is measurably faster; do not use quick runs, weaker output, or aggregate rankings to hide an unmet target.
- [ ] Promote conversion routes from Targeted to Established, Advanced, or ReferenceVerified only when the owning package adds the required reopen, realistic-fixture, visual or structural regression, and independent-producer evidence. Prioritize reverse PDF adapters, OpenDocument bridges, and OneNote, AsciiDoc, LaTeX, MHTML, and Visio routes that remain Targeted in the generated conversion catalog.
- [ ] Link every conversion support assessment to either an open roadmap outcome or an explicit intentional boundary, and expose that linkage in the generated route matrix. Fail catalog verification when any route gains a non-intentional limitation without an owner.
- [ ] Add handle-bound output creation and writing for report-producing tools so path authorization remains tied to the final file handles instead of a separate pre-write check. Cover symlink, junction, hard-link, and replacement races across supported operating systems in the shared path owner.
- [ ] Publish versioned, self-contained NativeAOT `OfficeIMO.Tool` release assets for supported Windows, Linux, and macOS x64/Arm64 targets in addition to the NuGet tool. Require exact-artifact startup and representative HTML/PDF workflow smoke tests, dependency and license inventory, checksums, SBOM and provenance, and release-page install instructions; keep one CLI command contract rather than a separate native implementation.

## Image engine

- [ ] Unify font resolution, baseline placement, glyph coverage, and shaping evidence across raster, SVG, and PDF. Extend the existing managed and optional HarfBuzz paths with identical font programs and script runs, including Greek/Cyrillic fallback, Arabic/Hebrew, Indic, CJK vertical text, combining marks, and emoji. Distinguish browser-native shaping from managed shaping, retain searchable logical text where the target supports it, and diagnose every stroke-font, outline, raster, or substituted-font fallback under the selected profile.
- [ ] Establish full-run, provenance-bound image performance regression gates across representative PNG, JPEG, TIFF, WebP, metadata, optimization, and resampling workloads. Track elapsed time, managed allocation, peak process and native memory, encoded size, fidelity, determinism, and cancellation latency; prioritize TIFF and WebP decode work only when corpus runs show a large, repeatable gap across supported operating systems.
- [ ] Add bounded ICC-to-sRGB conversion only after representative matrix, LUT, RGB, CMYK, and malformed profiles have an explicit color-correctness corpus. Keep the current byte-preservation and metadata-loss report separate from color conversion, and reject profiles that exceed the declared parser, pixel, or allocation limits.
- [ ] Evaluate lossy or animated WebP, JPEG-in-TIFF, and BigTIFF as separate products only when real consumer files establish the required decode, encode, fallback, animation/page-loss, and memory contracts.
- [ ] Add bounded EMF/WMF rasterization when older Office-document fixtures demonstrate a material fidelity gain. Keep ICO, PCX, BMP/GIF encoding, and uncommon or expensive codecs behind the caller-codec boundary until a first-party consumer justifies ownership.

## Desktop Studio

The next product target is a dependable desktop document workspace: a person can open a document, understand its limitations, perform a supported task, review the result, and save or recover it without losing work. The [Studio README](../OfficeIMO.Studio/README.md) owns current capabilities; the [distribution guide](../Build/Studio/README.md) owns existing package contracts. The phases below contain remaining work, including validation gaps where implementation already exists.

### Delivery order and dependencies

| Phase | Product outcome | Main owner | Dependency and completion evidence |
| --- | --- | --- | --- |
| 1. Consistent workspace | Commands, panes, inspectors, and notices behave consistently | Studio presentation and command layer | Builds on the adaptive shell; complete representative tasks at compact and wide sizes, with keyboard and expanded text |
| 2. Safe sessions and jobs | Users can interrupt, resume, recover, and publish work predictably | Studio host plus shared workflow/output owners | Define source identity and publication behavior before persistent queues; prove failure and recovery scenarios |
| 3. Everyday document work | Editing, page organization, comments, forms, OCR, and conversion form complete user journeys | Studio over PDF, Workflows, and Reader.Ocr | Uses phases 1-2; save, reopen, and independently inspect representative outputs |
| 4. Advanced review and production | Redaction, comparison, accessibility repair, preflight, and recipes expose reviewable results | PDF and Workflows first; Studio second | Admit each surface only when the corresponding engine contract and fixtures exist |
| 5. Desktop acceptance and distribution | Supported desktop builds are usable, accessible, installable, and upgradable | Studio platform adapters and PowerForge | Start native smoke tests early; finish the complete claimed OS and artifact matrix before distribution |
| 6. Optional desktop integrations | Native printing, scanning, and browser intake fit the same document workflow | Optional host adapters and shared owners | Requires source/output safety and a proven desktop package channel; each integration has its own acceptance gate |
| 7. iPad, then iPhone | A smaller touch-oriented product shares the document engines | Separate mobile host over shared presentation and engines | Requires a physical-device feasibility gate before a broader mobile commitment |

Phases 1-3 are the first desktop usability scope. Phase 5 supplies its platform and distribution acceptance; it is not postponed until every advanced feature exists. Phase 4 can deliver one independent capability at a time. Phases 6-7 do not block a useful desktop release. Calendar estimates should follow the first scoped implementation slices and reference-machine measurements; these dependencies are the planning baseline, not a delivery-date promise.

### Phase 1: consistent workspace

- [ ] Complete the visual system over Avalonia Fluent and the existing semantic brushes: shared typography, spacing, icon geometry, heights, focus rings, borders, and selection states. Start with 13-14 DIP body/control text, 12 DIP secondary labels, and a 4/8 DIP spacing scale; validate the values with real scaling and translations. Offer comfortable and compact density, remove remaining undersized labels and decorative hard-coded colors, and preserve document colors independently of the application theme.
- [ ] Introduce one command catalog for menus, toolbars, tool search, command palette, shortcuts, and enabled-state explanations. Organize application navigation around Home, Tools, and Jobs, with Read, Edit, Comment, Pages, Forms, and Protect inside a document. Preserve selection, zoom, scroll position, and unsaved work when changing modes.
- [ ] Extend recent documents with optional previews, remove/clear actions, and missing-file recovery. Distinguish opening a PDF from converting or assembling other formats before asking for files. Give thumbnail caches a retention limit.
- [ ] Replace long property forms with reusable contextual inspectors for text, images, annotations, forms, crop, and signature placement. Keep numeric geometry in an Advanced section, provide keyboard alternatives to dragging, and make preview, Apply, Cancel, and Undo behavior consistent. Distinguish replacement of existing text from adding a text overlay.
- [ ] Turn diagnostics into actionable notices for rendering substitutions, unsupported edits, conversion loss, missing OCR prerequisites, and protected-document restrictions. Give each notice a next action and optional page-linked details. Use consistent states for unsaved work, saved output, partial completion, cancellation, and failed publication while retaining the local diagnostics privacy contract.

Completion evidence: open a document, find text, switch modes, edit a supported object, undo, and save without losing context. Inspect Home, Tools, document, OCR, conversion, output, and health surfaces at 960 x 620, 1280 x 800, and wide sizes, including long labels, empty states, busy states, and errors. Controls must remain reachable without overlap; headless bounds tests supplement rendered inspection.

### Phase 2: safe sessions and jobs

- [ ] Extend full-storage and unavailable-volume acceptance to native Windows and macOS, preserving source bytes and usable recovery copies.
- [ ] Complete source/output identity checks across open tabs, OCR, conversion, assembly, recipes, and Save As. Exercise case rules, aliases, links, external replacement, read-only files, and provider-backed sources. Route reusable authorization and publication invariants through the shared owners rather than adding per-view checks.
- [ ] Extend StorageProvider usage beyond `Path.LocalPath` with stream access, permission lifetime, and bounded app-owned staging when a canonical engine requires a seekable local file. Preserve source identity and conflict detection; explain provider guarantees where atomic replacement is unavailable. Cover macOS sandbox access and Linux portal paths before reusing the adapter on mobile.
- [ ] Unify workflow presentation around inputs, intended result, output destination, preview, progress, cancellation, and next action. Introduce a Jobs surface over existing workflow execution with per-file status, bounded concurrency, retry of failed inputs, and result links. Cancellation must state whether any outputs were already committed; retry must not silently duplicate or overwrite them.
- [ ] Define shutdown and interruption behavior for active operations: wait, cancel safely, or leave a recoverable record where supported. Distinguish restoration of job history from resumable execution; resume a stage only if the shared runner proves source/configuration identity and safe restart semantics.
- [ ] Add deliberate failure scenarios for disk-full, denied output, interrupted writes, changed inputs, app termination, malformed recovery data, and another tab owning the destination. Verify preserved source bytes, explicit output state, useful recovery, and cleanup of task-owned staging data.

Completion evidence: interrupt a real edit and a multi-file workflow, restart, recover supported work, retry the failed input, and reopen the output. No successful-completion notice may describe a failed or incomplete publication. Existing save, cancellation, and recovery code is the starting point for this proof, not a reason to implement a second transaction system.

### Phase 3: complete everyday document work

- [ ] Complete direct manipulation for supported text, image, annotation, crop, and form operations with visible bounds, snapping where useful, keyboard movement, numeric alternatives, and predictable undo groups. Explain unsupported content before mutation; keep text replacement, overlay authoring, and source-document reconstruction distinct.
- [ ] Improve page organization for large selections: range selection, keyboard reorder, rotate, duplicate, import, extract, and split with a preview of the resulting page order. Keep reading position and selection meaningful after changes; verify page labels, bookmarks, links, forms, and signatures under the canonical preservation policy.
- [ ] Build anchored comment threads over existing reply and review-state APIs with author/status filters, next-unresolved navigation, resolve/reopen, and persistent selection. Extend annotation exchange only where needed for portable review handoff and verify replies and states in independent readers. Hosted collaboration remains a separate product decision.
- [ ] Complete form filling and authoring journeys with understandable field names, validation feedback, tab order, radio-group behavior, required/read-only states, and appearance previews. Keep filling, editing field definitions, and flattening distinct. Route missing form semantics to `OfficeIMO.Pdf` and verify exported values and appearances outside Studio.
- [ ] Standardize conversion, assembly, image export, optimization, and protection around the phase 2 workflow pattern. Show route-specific loss, output conflicts, signature consequences, and proposed filenames before execution. Provide open-result, reveal-file, inspect-report, and retry actions that apply to the actual result.
- [ ] Guide certificate-signing and protection tasks through certificate selection, appearance placement, permissions, save-copy behavior, and post-save inspection. Distinguish a visual signature appearance from a cryptographic signature, and document the actual validation policy rather than showing an unconditional trust badge.

Completion evidence: representative user journeys cover read/search, edit/undo, organize/export, comment/reopen, fill/flatten, OCR/search, convert/inspect-loss, and sign/inspect. Each journey has a producer fixture, saved-output reopen evidence, keyboard coverage, and relevant protected or unsupported cases. Engine limitations stay visible in the owning capability matrix.

### Phase 4: advanced review and production

- [ ] Integrate the reusable redaction recipe, decision, progress, batch, and evidence contracts into candidate discovery, page review, approve/reject, explicit output, and verification. Distinguish a pending mark from permanently removed content; preserve source-bound decisions and invalidate stale approvals when the input changes. Planning, OCR mapping, protected-document policy, and publication remain in shared owners.
- [ ] Present the shared comparison change model as linked panes, overlays, a navigable change list, and an exportable summary. Retain synchronized reading for simple comparison. Semantic changes, visual differences, inserted/deleted/moved pages, and scanned-page uncertainty depend on the PDF comparison outcome above; do not infer them from pixel differences alone.
- [ ] Expose imported-PDF accessibility remediation through page/object findings, reading-order and tag review, supported repair previews, and manual-review items. Depend on the PDF engine remediation outcome above and report the independent validation actually performed, including assistive-technology reading evidence.
- [ ] Expose production preflight profiles with page-linked font, color, image-resolution, transparency, output-intent, and page-box findings. Separate inspection, proposed fixups, accepted changes, and verified output; depend on the canonical preflight contract and independent validation.
- [ ] Project the shared typed workflow runner into saveable recipes and batch queues with dry-run plans, schema versions, per-stage budgets, safe output publication, and result history. Require the same serialized contract to run through `OfficeIMO.Tool`. Define which stages can resume and prevent saved recipes from silently authorizing new inputs or destructive changes.

Completion evidence: deliver each capability as an engine-to-Studio slice with realistic fixtures, reviewable decisions, deterministic reports, saved-output validation, and one non-GUI consumer where the contract is shared. A complete comparison or remediation editor is not a prerequisite for releasing the everyday workspace.

### Phase 5: desktop acceptance and distribution

- [ ] Add native macOS application/document menus and About, Settings, Hide, Quit, File, Edit, and Window behavior backed by the shared Studio commands. Validate title bars, full screen, primary modifiers, focus restoration, Windows keyboard/mnemonics, and Linux GNOME/KDE dialogs and font fallback on the chosen X11/Wayland backend.
- [ ] Automate the rendered state matrix across supported desktop systems: Home, document, Tools, OCR, conversion, output, health, empty, busy, error, and protected-document states. Cover compact/normal/wide windows, 100/150/200 percent display scaling, monitor changes, light/dark/high contrast, expanded translations, and keyboard-only tasks. Record failures by platform and fix them before claiming that platform's acceptance.
- [ ] Extend automation metadata with actual Narrator/NVDA, VoiceOver, and Orca task runs for tabs, custom page canvas, comments, forms, dialogs, and progress announcements. Fix exposed type names, duplicate page/thumbnail announcements, lost focus, and ambiguous selection. Distinguish an accessible application shell from an accessible document reading experience.
- [ ] Deliver reviewed Polish and German interface packs as the first proposed translation wave, followed by languages with a reviewer and user demand. Validate plural/format behavior, fallback, dialogs, diagnostics, and longer labels. Admit right-to-left language packs only with bidirectional layout and document-text interaction evidence; reserved culture names alone do not establish translation support.
- [ ] Establish reference-machine budgets for cold launch, first-page display, search, scrolling, zoom, edit feedback, cancellation, and retained memory using small, scanned, and long PDFs. Record baselines before selecting numeric limits, then bound render/thumbnail caches, virtualize off-screen work where necessary, cancel obsolete operations, and verify resource release through repeated open/close cycles.
- [ ] Complete exact-package install, launch, open/edit/save, upgrade, and uninstall evidence for every advertised OS/architecture combination.
