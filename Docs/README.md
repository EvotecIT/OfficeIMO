# OfficeIMO documentation

OfficeIMO documentation describes the repository as it works now. Package READMEs explain the public API, support matrices state tested coverage and limits, generated reports record reproducible evidence, and [ROADMAP.md](ROADMAP.md) owns open product work.

Historical implementation reviews, pull-request checkpoints, and release-wait notes are not maintained as product documentation. When a review finds a durable limitation, that limitation belongs in the relevant support matrix and the actionable work belongs in the roadmap. Completed work belongs in the owning package README or generated evidence.

## Generated evidence

Generated files state their source at the top and should not be edited by hand.

- `Compatibility/generated/` is produced by the compatibility generators described in [Compatibility/README.md](Compatibility/README.md).
- [HTML support](officeimo.html-support-matrix.md) is generated from the HTML capability and diagnostic catalogs.
- [PDF conversion support](officeimo.pdf-conversion-support-matrix.md) is generated from `pdf-conversion-scenarios.json`.
- [CommonMark inventory](officeimo.markdown.commonmark-inventory.md) and [GFM inventory](officeimo.markdown.gfm-inventory.md) are generated by the Markdown test suites.
- [Benchmark evidence](benchmarks/README.md) records reproducible performance runs and their provenance.

## Documentation ownership rules

1. Describe implemented behavior in present tense and link it to its public owner.
2. Put installation and usage examples in the package README that owns the API.
3. Put exact coverage and known limits in a support or capability matrix.
4. Put every open product item in [ROADMAP.md](ROADMAP.md); do not create another backlog, readiness review, gap plan, or product roadmap.
5. Keep dated reports only when the date is part of reproducible evidence, such as a benchmark run. Do not use dated reviews as living documentation.
6. Keep competitor comparisons on the public website when they help users choose a library. Repository documentation and API design use OfficeIMO contracts, standards, fixtures, and measured workloads as their vocabulary.
7. Update generated documents through their source catalogs or generators.
8. Remove obsolete planning notes after their current facts and open actions have been moved to the correct owner.
