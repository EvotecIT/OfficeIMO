# OfficeIMO PDF current state

`OfficeIMO.Pdf` is the first-party, dependency-light PDF engine for creating, reading, inspecting, rendering, converting, and safely changing business PDFs. This document describes the current product contract. Open PDF work is tracked in the repository [roadmap](ROADMAP.md), and direct conversion evidence is generated in the [PDF conversion support matrix](officeimo.pdf-conversion-support-matrix.md).

## Ownership

- `OfficeIMO.Pdf` owns PDF parsing, writing, layout, rendering, security policy, signatures, forms, annotations, manipulation, diagnostics, and compliance evidence.
- `OfficeIMO.Core` owns reusable vector/raster primitives, text measurement and shaping seams, codecs, colors, paths, clipping, and image export policy; drawing APIs remain in the `OfficeIMO.Drawing` namespace.
- `OfficeIMO.Html` owns HTML/CSS parsing, resource policy, layout, pagination, and its backend-neutral scene. `OfficeIMO.Html.Pdf` maps that scene into PDF primitives.
- Word, Excel, PowerPoint, OpenDocument, Markdown, RTF, OneNote, AsciiDoc, LaTeX, Email, EPUB, and Visio packages remain source-format adapters over the shared PDF and Drawing owners.
- OCR execution remains an optional caller/provider concern. PDF renders bounded requests, normalizes and de-duplicates provider words, preserves confidence and native/OCR provenance, and enriches the shared logical model without embedding an OCR runtime.

The machine-readable [`pdf-conversion-scenarios.json`](pdf-conversion-scenarios.json) manifest owns direct-adapter routes, composition routes, fidelity status, and proof ownership. The checked-in conversion matrix is generated from that manifest and checked for drift.

## Public workflow

- `PdfDocument.Create(pdf => ...)` is the normal authoring entry point. `Compose(...)` appends through the same closed builder model, and every supported flow boundary receives `PdfContentBuilder`; flow authoring is not duplicated on the root document. Incremental hosts use `compose.Settings(...)` for the document-owned `PdfCreateOptions` snapshot, while `Typography(...)` applies the shared Drawing font, fallback, language, and shaping profile to existing and future page snapshots. `Element(...)` is the uniform visual and semantic envelope over the normal scoped flow engine, including nested rows and multipage continuation, and explicit `Semantic(...)` groups remain one logical tagged-PDF structure element across page boundaries. Rows use fixed, automatic, relative, or percentage sizing and reject incompatible or zero-width mixed layouts. Keep constraints share one cursor-aware preflight path and reject content whose complete height cannot be known before rendering.
- `PdfDocument.Load(...)` is the normal read, inspect, and processing entry point.
- `PdfDocument.Read`, `Text`, `Images`, `Pages`, `Forms`, `Attachments`, `Bookmarks`, `Annotations`, `JavaScript`, `Stamp`, `Security`, `Redactions`, `Optimization`, and `Proof` expose focused workflow surfaces.
- `PdfDocument.Preflight(...)` provides non-throwing readiness and security evidence before a workflow is selected.
- `PdfDocument.Analyze(...)` provides the consolidated health, capability, diagnostic, optimization, signature, repair, mutation, and optional compliance report.
- `PdfDocument.CreateComplianceArtifact(...)` binds exact output bytes to internal readiness and external validator evidence.

Byte, stream, path, sync, and async entry points share the same engines. Caller-owned streams remain caller-owned. Extraction, splitting, merging, page import and form operations accept caller-selected read limits and cooperative cancellation through their existing owners. Remaining-stream input starts at the current position; rejected admission and cancellation before publication leave an existing destination unchanged. PDF save APIs generate and write the document synchronously; asynchronous saves await destination flushing and file publication. A cancellable opened-source save checks its token between bounded writes and after the final write. Caller-owned streams can retain a prefix after cancellation; staged path saves preserve an existing destination when cancellation occurs before publication.

Every adapter returns stable conversion evidence. `Faithful`, `FaithfulWithSubstitutions`, and `Degraded` are derived from structured warnings; producing a syntactically valid PDF alone is not a fidelity claim.

Category-axis/scatter-axis mixtures are rejected with an explicit warning instead of silently omitting a series. |

Word, Excel, and PowerPoint reference gates use pinned PDFs exported from the same checked-in fixtures with producer/version provenance, page geometry, source/reference hashes, semantic invariants, and recorded raster-distance budgets. A capability can be exact for a named invariant without claiming whole-document pixel equivalence.

The bounded Word running-story references cover inherited and explicit body typography, hidden/default/first/even headers and footers, blank section carriers, page fields, and tall stories that fit within the qualified page margins. The final 50-control comparison preserves ordered text, numeric multiplicity and page assignment, and glyph origins within 0.30 pt horizontally and 0.25 pt vertically. All 50 contact sheets were inspected. Watermark text proportions and image opacity still differ from Word; Cambria Math and general font/layout fidelity remain open. Two tall-story references also retain a 0.040009 pt page-width difference, so this evidence does not establish exact page-size equality. Exact-height body content extending beyond physical bottom margins remains a separate limitation.

The machine-readable [`pdf-reverse-conversion-scorecard.json`](pdf-reverse-conversion-scorecard.json) executes 56 matrix cases across seven independent producer fixtures and the DOCX, HTML, XLSX, PPTX, ODT, ODS, ODP, and PNG routes. Every case must open the source, serialize and reopen its target, retain route-specific semantic tokens, and prove editable structure, explicit omission reporting, or deterministic visual output. Separate generated stress cases cover image-only OCR, mixed native/OCR content, credentialed encrypted input, and recoverable malformed input. The comparison benchmark measures the same eight projections across five deterministic PDF producers and three workload scales after validating complete source content and route-appropriate target content.

OneNote conversion is a semantic-document projection, not a reconstruction of the free-form OneNote canvas. Email, EPUB, and Visio direct façades report their attachment/resource, pagination, preview, and semantic-fallback decisions rather than implying native-application equivalence.

Supplemental [independently authored English fixtures](../OfficeIMO.TestAssets/EnglishLayout/README.md) require complete ordered prose and table labels through native reading, DOCX, ODT and semantic HTML, plus typed XLSX/ODS cells with short, negative and repeated numeric values. Ordered comparisons normalize Unicode composition and whitespace only; every occurrence, punctuation mark and short number remains required. The spreadsheet checks retain editable numeric cells and explicit omission reporting for prose outside the tables. These finite fixture contracts do not establish general reconstruction accuracy or whole-document visual fidelity.

The opt-in column policy redistributes the existing total worksheet-width budget across detected proportions; `ColumnProportionsApplied` records successful mapping. It does not guarantee that every cell's contents fit. Structured reading can refine an existing text table to one complete closed grid when its row and column counts and original text assignments agree. This bounded profile uses ordinary, uniformly painted nonwhite horizontal and vertical rulings; incomplete or competing boundaries, uncertain paint, filled shapes, images and effects retain text-derived fallback. [Independent ruled ledgers](../OfficeIMO.TestAssets/TableGeometry/README.md) qualify the authored 240/72/96/120-point widths at page rotations of 0 and 90 degrees while preserving all 16 cells. Managed XLSX/ODS-to-PDF visual checks show complete description labels with the proportion option where equal widths clip them; narrow headers can still abut, font substitution remains reported, and ODS styling remains limited. Those checks cover the managed destination projection, not native Excel or ODS rendering.

## Deliberate boundaries and open product gaps

The engine already covers the common document-operation set expected from a
managed PDF library: authoring, page selection and composition, merge and
overlay, attachments, encryption, signatures, redaction, optimization and Fast
Web View, PDF 2.0, PDF/A and PDF/UA evidence, forms, annotations, structured
readback, and loss-aware format adapters. The remaining gap is mostly depth and
producer fidelity rather than a missing second API for the same operation.

The highest-value open areas are tracked in [ROADMAP.md](ROADMAP.md): remaining
difficult Type 3 programs and color/pattern/transparency rendering, broader native Office layout,
externally proven standards and producer corpora, deeper semantic PDF-to-Office
reconstruction, and optional provider packages for capabilities
that should not become core runtime dependencies. Browser JavaScript, TeX
execution, XFA execution, and automatic whole-document editable reconstruction
remain explicit non-contracts unless a separately owned, testable product shape
is adopted.

## Resources, fonts, and trust

The balanced default allows installed fonts plus bounded data URI and embedded-package resources. Arbitrary local-file reads and remote resolver calls remain disabled.

- `PdfResourcePolicy.CreatePortableDeterministic()` provides reproducible, host-independent behavior.
- `PdfResourcePolicy.CreateTrustedHost()` allows an application to opt into intended local or remote resolution.
- Conversion profiles control fidelity and content selection; they do not silently change trust.

Generated text can use registered TrueType or OpenType/CFF families without consuming the standard-font compatibility slots. Unavailable or non-embeddable fonts produce explicit substitution evidence. Readback exposes subset prefixes, embedding stream kind, encoding and ToUnicode health, declaration paths, and bounded parsed OpenType/TrueType program facts such as glyph count and Unicode cmap coverage. It does not treat the program glyph count as painted usage. The optional `OfficeIMO.Drawing.HarfBuzz` adapter provides full OpenType shaping through the Drawing provider seam without adding HarfBuzz to the dependency-light core packages. The [shared managed multilingual profile](../OfficeIMO.Core/README.md#managed-multilingual-shaping) supports bounded horizontal static-font Arabic joining and required ligatures, Latin/Hebrew/Arabic marks and selected contextual positioning, with complete original source clusters. Unsupported lookup composition, cursive/device/variation positioning and broader scripts remain explicit provider declines rather than complete-shaping claims.

Generated PDFs default to embedded-font Latin GSUB substitutions. The shared Core shaper selects the default `latn` language system, falling back to `DFLT` when Latin is absent, and enables `liga`, `clig`, `rlig`, and the language system's required feature. Optional features honor explicit settings; required features cannot be disabled. Latin membership follows the Unicode 17.0 Latin script repertoire, including IPA, phonetic modifiers, letter numbers, and fullwidth letters. Combining marks inherit a Latin base; Common punctuation is eligible only where adjacent strong scripts agree on Latin. Removed directional controls remain segment boundaries. Measurement, painting, extraction, search, and redaction share the resulting glyph ownership.

The managed subset covers bounded single, multiple, alternate, ligature, format 3 contextual and chained contextual, extension, and single-subtable reverse substitutions. Unsupported lookup flags, excessive lookup counts, contextual rules that change glyph count before a later record, and reverse lookups with multiple subtables retain scalar fallback with diagnostics. Pair kerning applies by default: OpenType GPOS or `kern` pairs for embedded fonts and Adobe AFM pairs for the standard Helvetica and Times fonts. Set `PdfCreateOptions.TextKerning = false` for nominal advances. Right-to-left and Arabic text is shaped and ordered automatically through the Unicode Bidirectional Algorithm (UAX #9), and line wrapping follows Unicode line breaking (UAX #14). Each run is written as one `TJ` array, and embedded fonts are tagged, compactly renumbered subsets. Indic, Thai, and other complex scripts still need a full shaper through `TextShapingProvider`, such as the HarfBuzz adapter, which shapes each script and bidi run separately.

## Mutation and security policy

Preflight chooses a supported full rewrite, append-only revision, or refusal. Mutation reports prove byte-prefix, revision-chain, signature-range, DocMDP/FieldMDP, and preservation state where those properties matter.

- JavaScript and XFA are never executed.
- A signature object is not described as preserved when its signed byte range is invalidated.
- Catalog, page, resource, form, annotation, attachment, layer, tag, metadata, action, and security structures are not silently dropped during rewrite.
- Secure redaction, signature validity, and compliance require the appropriate cryptographic, residue, render, or external-validator evidence.
- Unsupported or ambiguous repairs remain diagnostics rather than guessed mutations.

The PDF evidence lanes cover cold and cached analysis, SVG/PNG rendering, buffered serialization, forward-only object serialization, shaping, managed peak memory, largest transient buffers, deterministic bytes, and bounded hostile inputs. A strict provenance-bound scorecard runs inspection, semantic recovery, font and image readback, managed rendering, all mutation plans, and declared-compliance claim assessment on pinned Open Preservation Foundation and veraPDF artifacts across supported CI operating systems.
